GitHub 页面导览

你的仓库：github.com/365649649-droid/20261026 — 只需要看懂 4 个页面

先建立一句话的理解：GitHub 就是「云端的项目文件夹」+「一台免费帮你跑测试的电脑」。
你本地改完代码推上去 → 云端那台机器自动装依赖、跑 pytest → 结果以一个 绿色勾 或 红色叉 显示在网页上。
下面这 4 张图全是你自己仓库的真实截图，按顺序看一遍，以后再打开就不会迷路。

1仓库首页 —— 你 90% 时间待的地方

打开仓库链接后默认就是这个页面。记住图里 4 个红框就够了。

  • 1Actions 页签 —— 自动测试的成绩单。每次推代码，这里会多一条记录，绿勾=通过，红叉=失败。这是你以后每天必看的地方。
  • 2绿色 Code 按钮 —— 点开能复制仓库地址（HTTPS / SSH）。作用就是「把地址抄下来给 git 用」，不是用来下载 zip 的（虽然也能下）。
  • 3Commits（这里显示 6） —— 这个仓库一共保存了 6 次。数字就是提交次数，点进去看每次改了什么。
  • 4文件列表 —— 左边是文件名，中间是「最后一次改它的说明」，右边是「多久之前改的」。这个列表 = 你本地文件夹在云端的镜像。
可以完全忽略的部分：Issues、Pull requests、Projects、Security and quality、Insights —— 这些是多人协作/项目经理用的，一个人学自动化测试用不上。右上角的 Star / Fork / Notifications、右边的 About / Releases / Contributors / Languages 也都不用管。
只记住一件事：页签栏里你只点 Code 和 Actions 这两个。

2Commits —— 每次保存的历史记录

相当于「文件的历史版本」。想查「哪一步开始出问题的」，就从这里翻。

  • 1每行 = 一次保存。上面写的是你 commit 时写的说明，比如「docs: 补充 CI 实测踩坑记录」。
  • 2右侧的 aeacd6f —— 这次保存的编号（提交号），全世界唯一。它就是「这次」的名字，日志里、报错里都用它指代某一次保存。

图里最关键的一列是那个小徽章：
✓ 1/1 = 这次提交触发了 1 个检查，1 个全过；
✗ 0/1 = 这次提交挂了，0 个通过。
你之前故意弄红的那次（test: 故意让 CI 红一次）就是 ✗ 0/1，一眼就能看出来是哪次坏的 —— 这叫 bisect 思路：找第一根红叉，问题就在它和上一个绿勾之间。

3Actions —— 云端跑测试的「成绩单」

这个页面就是那台免费电脑的工作记录。你的 ui-tests.yml 让它在你每次 push 时自动跑 pytest。

  • ✓最左边一列圆点：绿色勾 = 这次全部通过；红色叉 = 这次有失败。先看这一列，其它文字都可以先不看。
  • 2每一行 = 一次运行，主标题是触发它的那次提交说明（比如「docs: 补充 CI 实测踩坑记录」），下面小字是 UI Tests #6: Commit aeacd6f —— 序号 + 提交号。
  • 3右边两列：什么时候跑的、跑了多久（17s / 55s / 1m16s）。耗时突然暴涨通常就是网络慢或某个等待没生效。

表头上的 Status 可以点，能筛选「只看失败」；Search runs 输入提交号能直接定位。
左边栏的 UI Tests 是你的 workflow 名字（一个仓库可以有多个 workflow，你现在只有一个）。

4点进红叉 —— 失败原因在哪里看

在 Actions 列表点任意一次运行，就进到详情页。下面这张是你最早那次失败（#1 b016598）的真实截图。

  • A顶部标题 + 红叉：哪次提交、编号多少。#1 是运行序号。
  • BStatus: Failure 和 Total duration 17s —— 只跑了 17 秒就挂了，说明是在「装环境」阶段死的，测试代码压根没跑。这种「秒挂」和第 3 节里那些跑了 55s~1m16s 的，是完全不同的问题类型。
  • C中间的 job 卡片（Playwright + pytest，红叉，13s）—— 一个 workflow 可以由多个 job 组成，红叉说明是这个 job 挂了。点它能看完整日志。
  • DAnnotations —— 最重要的一块。GitHub 会把错误摘要直接摘出来，不用点开日志就能看到原因：
    No file in D:/a/20261026/20261026 matched to [**/requirements.txt or **/pyproject.toml]
    翻译：在你仓库里找不到 requirements.txt。这正是当时红灯的真实原因 —— workflow 里写了 cache: pip，但仓库里没有依赖清单文件，GitHub 在缓存那步就报错退出了。后来补上 requirements.txt 就绿了。

看失败的固定顺序：红叉 → 看总耗时（判断是环境问题还是测试问题）→ 看 Annotations（80% 的情况这里就够了）→ 还不明白才点 job 名字翻日志。
如果 workflow 里配置了上传截图（我们配了），失败时还能在页面底部的 Artifacts 区下载 failed-screenshots 压缩包。

6你可能会遇到的疑问

为什么我打开的页面，和你截图长得不完全一样？
两个原因：① GitHub 会改版，按钮位置偶尔挪；② 这张截图是没有登录的状态，你登录之后会多出通知铃铛、Watch、Settings 等按钮。功能的相对位置不变。
页面转圈 / 打不开，或者图片加载不出来？
GitHub 在国内直连经常半通不通。开代理时注意选「全局」或把 github.com、githubusercontent.com 加进规则模式，否则会卡在白屏。这就是我截图时用代理的原因。
详情页右侧写着「Sign in to view logs」？
看完整日志要登录。但 Annotations 不登录也能看，错误原因基本都在那里，够用了。
红了就说明我的代码写错了吗？
不一定。按经验排序：依赖装不上（缺 requirements.txt、包名写错）> 超时（国内访问 saucedemo 慢）> 断言失败（这才是真的测试用例挂了）> GitHub 自己抽风。所以要先看 Annotations 第一行再判断，不要看到红就改代码。
为什么我 git push 完它自己就跑起来了？
因为 .github/workflows/ui-tests.yml 开头写了 on: push —— 只要往 main 分支推代码，GitHub 就自动触发。你也可以在 Actions 页用「Run workflow」按钮手动触发（需要 workflow 里配 workflow_dispatch）。
改完代码到看到绿勾，一般要多久？
你的项目实测 17s～1m16s，主要是装依赖和访问 saucedemo 的时间。推完代码刷新 Actions 页，等 1 分钟左右就有结果。

7以后的标准动作（3 步）

  1. 本地改代码，跑 python -m pytest 确认本地是绿的（本地都不绿，云上一定红）。
  2. 提交并推送（三条命令，或者直接让我帮你推）。
  3. 打开仓库 → Actions → 看最上面那条是绿勾还是红叉。红了就点进去看 Annotations。

每天真正要看的只有一个页面：Actions。Code 页签是「看代码在哪」，Commits 是「查历史」，只有 Actions 是「告诉我好没好」。
